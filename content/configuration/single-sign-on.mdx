# Single sign-on

The optional Logi identity provider lets a clan website reuse the member's Logi
sign-in. Each site keeps its own secure session cookie. A website redirects the
browser to Logi; an active Logi session completes the redirect without another
Discord sign-in. Cookies and signing secrets are never shared between sites.

The provider is disabled by default. An operator must configure it and verify the
target website before enabling it. Dashboard users need to sign in once after the
durable-session upgrade. See the [operator contract](https://github.com/Ninjonik/logi/blob/main/docs/integrations/website/sso-provider-contract.md)
for configuration, rollout, and validation requirements.

## Register a website

A workspace administrator can create an application in **Settings → Clan website and sign-in → Single
sign-on applications**. Give it a recognizable name, its HTTPS website URL, and
the exact HTTPS callback URL supplied by the website backend. Fragments,
credentials in URLs, and wildcard callbacks are rejected. The client secret is
shown once; store it in the website backend's secret configuration.

Register the website only with the minimum required access. SSO authenticates the
person; it does not grant an administrator role. Website authorization uses the
separately configured membership API and its current game-specific role policy.
An unavailable, stale or removed membership must not leave a cached admin grant.

When a user has no Logi session, authorization starts Discord sign-in immediately
and creates a normal Logi session before returning to the website.

## Website integration

| Purpose | Endpoint |
| --- | --- |
| OIDC discovery | `/.well-known/openid-configuration` |
| Authorization | `/api/sso/authorize` |
| Token exchange | `/api/sso/token` |
| Userinfo | `/api/sso/userinfo` |
| Public signing keys | `/api/sso/jwks` |

Use authorization code flow with PKCE **S256**, `openid profile` scopes, and fresh
state and nonce values for each attempt. A maintained OIDC client should verify
the RS256 signature against discovery/JWKS, the fixed issuer, audience, expiry,
nonce and state, and compare userinfo with the verified identity. Client
authentication uses `client_secret_post` from the backend. There is no refresh
grant; after the one-hour access token expires, start another authorization
redirect to reuse the still-active Logi session.

Userinfo contains only `sub` (the exact Discord account ID), `name`, `picture`,
`guild_id` (the canonical Discord guild ID), and `sid` (the central Logi session ID).
Role grants, platform IDs, private notes and storage records are not identity
claims. The website must bind its local session to the same `sub`, `sid` and
`guild_id` in the verified ID token and userinfo.

## Logout and access changes

Signing out of Logi revokes that central session, including its outstanding SSO
grants. Global Logi logout also revokes the user's other central sessions. User
identity changes, application deletion and central session expiry invalidate the
affected access tokens. Websites enforce these changes by checking userinfo on
protected requests and denying access if it cannot be validated.

Use the sign-out button in Logi to end a session. Logout requires a same-origin
POST; visiting a logout link does not change sessions. A successful logout
redirects to the sign-in page.

Signing out on a website ends that website's local session. It does not silently
sign the person out of Logi. Logi does not advertise RP-initiated or back-channel
logout; connected websites must not rely on an unimplemented notification.

If Logi cannot persist a logout, it reports a failure and retains the cookie so
the user can retry. It does not claim that other sessions were revoked.
