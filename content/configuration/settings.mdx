# Server settings

Server settings belong to the active workspace. Only managers should change them, and changes can affect how the dashboard, Discord coordination, events, and membership features behave.

Every configuration screen shows its scope above the editor. One game icon means
the change applies only to that selected game; a row of active game icons means
the change is clan-wide. Confirm that scope before saving settings, ticket
panels, membership workflows, or System operations.

## Change settings carefully

<Steps>

### Confirm the workspace

Check the server name in the sidebar before changing anything. Settings apply to that server, not to every community you can access.

### Change one concern at a time

Review the relevant section, make the smallest intended change, and save it.

### Verify in the affected feature

For example, after a scheduling or Discord-related change, inspect an event or the related Discord configuration rather than assuming the setting took effect as expected.

</Steps>

## System area, API keys, and Discord metadata

### Preview a Wardogs League match

For scheduled discovery, manual tracking and persistent Discord cards, see [Wardogs League tracking](/wiki/configuration/league-tracking). The standalone preview below remains available without registering a match.

Select **Wardogs**, then open **System → Imports → Wardogs League match**.
Paste a public `https://wardogsleague.net/matches/{id}` link and choose **Load match**.
The preview shows the schedule in Europe/Prague, teams with their factions,
map/zone/lighting, public hosting, moderator, map voting, rules and preparation steps.
Team member counts describe the team profile; they are not the match roster.
Reading the link does not create an event or confirm results.

No League account or Team API key is needed. Logi refreshes on request, at most
once every five minutes per match. If a refresh fails, the last saved match
remains visible with a stale warning, collection time and next allowed refresh.
Missing fields remain unknown. Only the Scheduled page format has live validation;
results, placements and no-show interpretation are not supported yet.

Website backends can request the same preview with an API key explicitly granting
**Public Wardogs League matches** (`league-matches`) and **Wardogs**:
`GET /api/v1/clan/league-matches?game=wardogs&url=<URL-encoded-public-match-link>`.
Poll every 5–10 minutes and honor `nextRefreshAt` and `Retry-After`. Inspect `stale`
and `fetchedAt` before presenting cached data as current. Legacy full-access keys
do not grant this new read. Server passwords and join IDs are never returned.

## Games

The **Games** section controls which games are active for this workspace:
**Hell Let Loose**, **Hell Let Loose: Vietnam**, and **Wardogs**. A workspace
may enable any combination, including none while it is being configured.

Game-specific settings are edited after choosing that game in the dashboard.
This includes game-specific Discord channels/wording where configured and
membership-application categories. Shared Discord identity, workspace-level
settings, and platform links are not duplicated per game.

When no games are active, Logi prevents creation of game-owned records and
links to this settings section. When exactly one is active, creation pages
select it automatically. With multiple games active, starting a game-owned
creation flow from **All games** first asks the manager to choose a game.

The manager-only **System** area groups Website API keys, Google Calendar sync, single sign-on applications, website event commands, Imports, Helper data, and Webhooks into collapsed sections. Normal Clan settings contains game, frontend, and Discord configuration. Treat keys, webhook signing secrets, and secret configuration as sensitive: never paste them into articles, roster notes, public screenshots, or support messages.

Each website API key belongs to the currently selected workspace. Its permissions
determine which data it can read or change. Give it a recognisable name of at most 80
characters. The full value is displayed once, at creation time; afterward the
dashboard shows its prefix, creation date, granted resources/games, and whether
it has been revoked. Revoking a key takes effect for future requests and cannot be undone:
create and deploy a replacement key before revoking one used by a live site.

#### Read-only integration keys

In **System → Website API**, the form starts with **Read-only** access and
only **Event summaries** and **Match summaries** selected. Choose the required
games explicitly; an empty resource or game selection cannot create a restricted
key. Review the selection, enter a name and press **Create read-only key**.
Copy the revealed key before hiding it or leaving the workspace. It is never
available from the existing-key list.

Choose **Full access (legacy)** only when an integration needs write access.
That mode can read and modify all clan data across all games. Existing keys
keep their permissions; restricted and legacy keys are clearly distinguished
in the list. To change a policy, create a replacement key, switch the integration,
and then revoke its old key. The interface is localized in English, Czech and German.

Administrators can also issue a restricted key through the existing authenticated
`POST /api/servers/{serverId}/api-keys` endpoint by including a `readAccess`
object alongside `name`:

```json
{
    "name": "Website summary reader",
    "readAccess": {
        "resources": ["event-summaries", "match-summaries"],
        "gameIds": ["hell_let_loose", "wardogs"]
    }
}
```

Both arrays must be nonempty and contain no duplicates. Resources can be
`server-snapshots`, `integration-health`, `event-summaries`, `match-summaries`, `events`, `groups`, `rosters`,
`assignments`, `stratmaps` or `matches`; game IDs
can be `hell_let_loose`, `hell_let_loose_vietnam` or `wardogs`. Each collection
request must select explicit permitted games. Missing `game`, `game=all`,
ungranted resources and all writes return `403 insufficient_scope`. Detail
reads check the stored tenant and game. Revocation is checked on every backend
operation, and restricted reads are not cached by HTTP clients.

Requests without `readAccess` still create full-access legacy keys, including
the form's explicit full-access option. Existing keys are not automatically restricted.
Use a newly issued restricted key for a read-only website and revoke the old
credential after switching it. The management list endpoint includes the stored
policy. A bearer key cannot create or broaden keys; that requires a dashboard
administrator session.

Restricted keys do not grant metadata, settings, raw users, calendar items,
presets or performance history in this first release. Read-only records still
require publication review: never publish raw API responses. The
[versioned website handoff](https://github.com/Ninjonik/logi/blob/main/docs/integrations/website/v0.5/README.md)
describes field allowlists, safe synchronization, fixtures and rollout order.
Deploy the compatible backend before using these new policies; an older backend
does not enforce them.

For website event and result listings, use `GET /api/v1/clan/event-summaries`
and `GET /api/v1/clan/match-summaries`, with an explicit game. These return
only identity, title, schedule/status or a minimized imported result. They
exclude passwords, notes, signup/player identities, source URLs and raw
telemetry. Each summary resource requires its own grant; it does not grant
access to the raw `events` or `matches` resource, or vice versa.

Both summary detail routes use the Logi event ID. Match summaries exclude
training events. No stored event result means `resultState: "unknown"` and
`result: null`; an imported event result is `provisional`, including for
concluded events. The website still approves publication and translations.
These routes do not provide human result confirmation or public-member consent.

Website integrations use the versioned API at `/api/v1`. Clan API requests
use `Authorization: Bearer <API key>`. Game-owned clan data uses **Hell Let
Loose** for legacy keys when no `game` query parameter is supplied, including legacy records;
use `game=hell_let_loose_vietnam`, `game=wardogs`, or `game=all` to select
another scope. List requests are cursor-paginated, default to 25 records, and
are capped at 100 records. Every game-owned returned record has an explicit `gameId`, so a
website can safely cache and combine data from more than one game. The live,
machine-readable contract is available at `/api/v1/openapi.json` and the
interactive reference at `/api/v1/docs`.

Start with the API key in an `Authorization` header; never put it in a URL or
client-side bundle. The key is tenant-scoped: it can access only the workspace
that created it and only operations permitted by its policy. A record ID from
another workspace is not usable. Writes below require a legacy full-access key.

```bash
curl -H "Authorization: Bearer YOUR_API_KEY" \
  "https://YOUR_LOGI_HOST/api/v1/clan/events?game=wardogs&limit=25&updatedSince=2026-01-01T00:00:00Z"
```

List responses contain `data` and `page.nextCursor`. Treat that cursor as an
opaque value: send it only to the same resource with the same `game` and
`sort=createdAt` selection. To retrieve one known record, use
`GET /api/v1/clan/events/{id}`. `updatedSince` accepts an ISO timestamp and is
useful for incremental synchronization; it includes records updated at or
after that time.

For a write, generate one new visible idempotency key and retain it until the
request is resolved. If a network timeout leaves the result unknown, repeat
the exact method, URL, body, and key to receive the original result. Reusing a
key for changed content returns `409 idempotency_conflict`, so changed work
needs a new key. Invalid inputs return `400` with
`{ "error": { "code": "validation_error", "message": "..." } }`.

```bash
curl -X POST "https://YOUR_LOGI_HOST/api/v1/clan/events" \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: event-create-42" \
  --data '{"kind":"training","name":"Training","registrationEnd":"2030-01-01T18:00:00Z","meetingStart":"2030-01-01T19:00:00Z","pingClan":false}'
```

Roster and member synchronization can use `updatedSince` on their respective
list endpoints. Member pages contain one record per workspace member even when
that person has assignments in multiple games.

The API currently supports article writes, group create/update/delete, event
create/update, stratmap create/update, topic-preset create/update, squad-preset
create/update, roster update/delete, assignment create/update/delete, the named
event conclude action, and event signup changes. Event
deletion is intentionally unsupported because its roster, match, Discord, and
scheduled-job dependencies have no safe deletion lifecycle. Every write requires an `Idempotency-Key`; repeating the
same request with the same key replays its original result for 24 hours. Group
deletion also clears that group's references from workspace assignments. An
event signup request uses
`POST /api/v1/clan/events/{eventId}/signup` with a JSON `userId` and `group`
(a group string or `null`). It applies the same signup eligibility and
registration-window rules as the dashboard.

Event creation and updates use `POST /api/v1/clan/events` and
`PATCH /api/v1/clan/events/{eventId}` with the same complete event form used by
the dashboard. Referenced signup groups, stratmaps, and topic presets must
belong to the authenticated workspace. Successful creates emit `event.created`;
updates and `POST /api/v1/clan/events/{eventId}/actions/conclude` emit
`event.updated`.

Stratmaps and presets use `POST /api/v1/clan/stratmaps`,
`POST /api/v1/clan/topic-presets`, and `POST /api/v1/clan/squad-presets`, with
the corresponding `PATCH /{id}` paths for complete dashboard-equivalent
updates. These resources are intentionally non-deletable: existing event,
roster, and Discord-forum references do not have a safe cleanup lifecycle. A
stratmap's referenced event must belong to the authenticated workspace and use
the same game. Topic preset attachment limits are the same as the dashboard.

Roster updates use `PATCH /api/v1/clan/rosters/{rosterId}` and must include the
complete roster form for that same event. Only unpublished rosters can be
deleted. Assignment changes use `/api/v1/clan/assignments`; they rebuild the
workspace and user membership state and synchronize open matching-game rosters.
An assignment cannot be moved to another user or game through `PATCH`. Logi emits one
`roster.updated` webhook after a roster write, or after an assignment change
that updates at least one open roster.

`PATCH /api/v1/clan/settings` changes only explicitly supplied safe workspace
and Discord fields. It cannot write runtime credentials, player-stat tokens,
ticket or membership workflows, or game overrides; omitted settings remain
unchanged.

<Callout type="warning">
    Do not rotate, delete, or reveal an API key unless you understand every
    integration using it. A broken key can interrupt an external integration
    immediately.
</Callout>

### Webhooks

System administrators can add an HTTPS webhook endpoint and send a test event.
Logi signs the exact JSON payload using `X-Logi-Signature` as
`sha256=<HMAC_SHA256(timestamp + "." + rawBody)>`; use `X-Logi-Timestamp` to
reject stale requests. The signing secret is revealed only when a subscription
is created or rotated. Current mutation events include article creation, update, and
deletion; event creation and updates; and roster updates caused by API event-signup changes. Failed transient deliveries retry with bounded backoff; permanent
4xx responses do not retry except `408` and `429`. Delivery history records
successful, failed, and retried attempts; deleting or disabling a subscription
prevents queued deliveries from being sent.

Each delivery is an HTTP `POST` with `Content-Type: application/json` and
`User-Agent: Logi-Webhooks/1.0`. The body has this exact JSON envelope. The
`id` is a UUID identifying the event; `X-Logi-Delivery` is the persisted
delivery-attempt ID and is intentionally different.

```json
{
    "id": "UUID event ID",
    "type": "event.updated",
    "createdAt": "2026-09-26T10:00:00.000Z",
    "guildId": "your-discord-guild-id",
    "resource": { "type-specific API response data" }
}
```

The request also includes `X-Logi-Event` (the same value as body `type`),
`X-Logi-Delivery`, `X-Logi-Timestamp` (Unix seconds), and
`X-Logi-Signature`. Verify a delivery before parsing or acting on it:
calculate HMAC-SHA256 over the exact `X-Logi-Timestamp`, a dot, and the raw
request body with the signing secret, then compare it to
`X-Logi-Signature` and reject timestamps outside your allowed replay window.
The signature is formatted as `sha256=<hex digest>`. A disabled or deleted
subscription stops pending deliveries from being sent.

Saving a channel or role selection does not prove that the bot can use it. The
bot must still be in this Discord server, be running, and have the channel and
role permissions required for the relevant action.

| Announcements channel       | Event announcement messages                                                        | No announcement is created there.                                                                                                                                                                     |

Removing the configured channel clears the stored panel state after cleanup is attempted.                                                                    |
| Forum category              | Match forum-post provisioning                                                      | A match cannot get a Logi forum post from the workspace default.                                                                                                                                      |

creation. Those message locations are then retained for that event; later

### Google Calendar sync

Clan managers can create a separate private iCalendar subscription link in the
manager-only **System** area. Add it in Google Calendar through **Other calendars → From URL**.

## Game server data

In **System → Game server data**, managers can enable, disable and resume sources
prepared by the Logi operator for this workspace. With no configured sources,
the section shows an empty state. The form never asks for a server password.
The operator supplies the provider address and token privately before activation.

HLL CRCON supports current server data and historical match collection. Wardogs
RCON supports current server data after checking its available functions. An
optional Wardog Servers directory source provides public status with attribution.
The **Wardogs Warcon** provider reads an existing Warcon panel, including live
players and completed matches. It is distinct from a direct Wardogs RCON source.
Select one source for a server; Logi does not silently replace it with another.

Cards show players, map, last observation, data freshness and any provider error.
HLL and Warcon also show the number of collected sessions and last successful history
import. Zero players is a known value; unknown is different. Old counts remain
visible with their timestamp when a source fails. Data becomes stale after three
minutes and unavailable after fifteen; disabling a source makes it unavailable
immediately. A missing directory entry does not prove that the server is offline.

**Disable** stops collection and rejects in-flight results from older runs.
If access or configuration is rejected, ask the operator to fix it and use
**Enable / resume**. **Refresh** reloads Logi's stored status; it does not contact
the game server. A history-import error is displayed separately from current data.

Website keys need the **Server snapshots** and/or **Integration health** grants
and an explicit game. Read `/api/v1/clan/server-snapshots?game=wardogs` or
`/api/v1/clan/integration-health?game=hell_let_loose`; details use the Logi
connection ID. These are read-only resources. Provider credentials, addresses
and private player identities are excluded. Live scores and imported sessions
remain unconfirmed; they do not create a verified player link or approved match
result. No game-server controls are provided by this screen or these API routes.

Discord server managers can also use `/server-status` with a game to see a private
summary of stored observations and their freshness. The command does not trigger
collection; the full connection list stays in settings.

### Warcon live scoreboard and website reads

An enabled Warcon connection has a **Live Warcon scoreboard** panel. Expand it
to see current players, faction scores, kills/deaths, K/D, cash, ping and the game
join code. It refreshes every 15 seconds while open in a visible tab. Its refresh
button requests a live view, which can reuse a shared ten-second cache.

Player and status timestamps are separate. This live view becomes stale after
45 seconds and unavailable after three minutes; unavailable player rows are
hidden. These thresholds differ from the stored snapshot card above. Missing
values are unknown, while a displayed zero is a measurement. Failed reads show
an error instead of leaving a player table labeled as current.

For the website, create a read-only key with the explicit **Warcon gameplay
data** grant and **Wardogs** selected. Legacy full-access keys do not implicitly
include it. The grant includes game display names and Steam IDs; only publish
those according to your community's policy. Keep the key in your website backend.

Read `/api/v1/clan/warcon-data/{connectionId}?game=wardogs&view=live`. Other views
provide analytics, cash history, match pages/details, leaderboard, seen players,
career, kills, catalogs, rotation and API health/capabilities. See the
[Warcon integration guide](https://github.com/Ninjonik/logi/blob/main/docs/integrations/website/v0.11/README.md)
and [API documentation](/api/v1/docs) for parameters and permissions. Map filters
use IDs from the catalog, which can differ from live display names.

A disabled kill feed remains disabled; Logi does not turn it on. Imported matches
and player observations remain unconfirmed and do not establish account ownership.
The scoreboard and website API provide reads only. Ban lists, staff notes, private
server configuration and administrative actions are outside this integration.

Changing a data source and managing website API keys require a current signed-in
administrator. Logi checks the session and workspace permission again when saving
the change. A pending Warcon read also rechecks access before returning provider
data. After signing out or losing administrator access, refresh the page and sign
in with an authorized account before trying again.

Wardogs League refreshes honor the provider's retry delay, up to 24 hours per
response. Existing saved data remains visible with its age while refresh is
unavailable; a provider error never replaces it with an empty match.

## Imports, performance, and helper data

The **Imports** section is manager-only operational maintenance. Each action uses
the game selected in the dashboard game switcher; when no game is selected, it
defaults to **Hell Let Loose**. The exact
member-import and linking safeguards are documented in
[Members and groups](/wiki/configuration/members). Two other controls are easy
to misunderstand:

- **Refresh performance history** rebuilds the workspace and player trend
  snapshots from recorded, non-training events with imported match statistics.
  The charts retain at most the ten most recent qualifying matches. It does not
  import a scoreboard, create a match result, or change a member's stored
  all-time performance summary.
- **Initialize helper data** first clears helper data, then creates the bundled
  default group hierarchy and one HLL Standard Lineup squad preset. It does not
  restore previously customised groups, topic presets, or squad layouts.
- **Reset helper data** deletes this workspace's groups, squad presets, and
  topic presets. It also clears group selections from assignments, topic-preset
  selections from events, and squad-preset selections from rosters. It leaves
  people, assignments, events, and rosters themselves in place. There is no
  recovery action in the dashboard.

Use reset only when deliberately starting these helper structures over, and
check events and rosters afterward because their preset references will have
been removed.

### Durable website synchronization

Restricted integrations can recover changes with `GET /api/v1/clan/changes` and
refetch minimal records atomically with their revision at
`GET /api/v1/clan/sync-records/{resource}/{id}?game=wardogs`. Both require explicit
underlying read grants and one game. Capture `start=now` before a baseline sweep,
then replay its signed cursor. Continue empty pages when `hasMore` is true.
Store decimal revisions losslessly. After seven days without recovery, a 410
`reset_required` response requires a new baseline. Keep CMS/publication decisions
in the website's own backend.

The registered projections are event summaries, match summaries, reviewed result
summaries, server snapshots and integration health. Optional `integration.changed` webhook subscriptions emit
minimal invalidations from dashboard, API, bot, import and collector transactions.
Use the existing administrator-session webhook endpoint to opt into that event
type; existing subscriptions are unchanged. The queue processes bounded batches,
honors Retry-After and recovers expired worker leases. Receivers must deduplicate;
the change feed remains the recovery source. See `/api/v1/docs` for the contract.

### Reviewed result access

Select **Reviewed result summaries** explicitly when creating a restricted key;
the existing event/match defaults do not include it. Read
`/api/v1/clan/result-summaries?game=hell_let_loose`, or a detail using its event ID.

## Discord membership integrations

Create a read-only key with the Discord membership resource and selected games in
Website API. Open Discord membership integrations, refresh, enter the allowed role
IDs per game, enable the policy and save. Blank role lists share only presence and
Logi assignment. Policy administration requires your signed-in server administrator
session; API keys cannot change these permissions.

Membership reads return an explicit unknown state when fresh Discord evidence is
unavailable. They never expose all roles or grant website administration. Policy
changes and reconnects invalidate cached authority. Membership feed consumers must
specify one Discord subject and handle a scope reset; membership webhooks require an
explicit `membership.changed` subscription. Existing summary keys and webhook
subscriptions do not gain member access automatically.

## Website event commands

A connected website may create, update or cancel events through its own service
key only when a manager enables a policy for it. Open **System → Website event
commands**, choose the registered single sign-on application, and for each live
restricted API key enter the allowed Discord role IDs per game (one ID per line),
tick **Allow event commands with this key** and save. Saving grants event-command
write access for the games that have at least one role; a game without roles stays
read-only, and disabling the policy removes the grant again.

The form only offers restricted keys of the current workspace and applications
registered in it; legacy unrestricted keys never qualify. Members must also hold one
of the listed roles in a fresh Discord observation when the website issues a
command, so a role list is a ceiling, not a guarantee. Policy administration needs
your signed-in server administrator session; API keys cannot change it.
