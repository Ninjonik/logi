# Server settings

Server settings belong to the active workspace. Only managers should change them, and changes can affect how the dashboard, Discord coordination, events, and membership features behave.

## Change settings carefully

<Steps>

### Confirm the workspace

Check the server name in the sidebar before changing anything. Settings apply to that server, not to every community you can access.

### Change one concern at a time

Review the relevant section, make the smallest intended change, and save it.

### Verify in the affected feature

For example, after a scheduling or Discord-related change, inspect an event or the related Discord configuration rather than assuming the setting took effect as expected.

</Steps>

## System area, API keys, and Discord metadata

## Games

The **Games** section controls which games are active for this workspace:
**Hell Let Loose**, **Hell Let Loose: Vietnam**, and **Wardogs**. A workspace
may enable any combination, including none while it is being configured.

Game-specific settings are edited after choosing that game in the dashboard.
This includes game-specific Discord channels/wording where configured and
membership-application categories. Shared Discord identity, workspace-level
settings, and platform links are not duplicated per game.

When no games are active, Logi prevents creation of game-owned records and
links to this settings section. When exactly one is active, creation pages
select it automatically. With multiple games active, starting a game-owned
creation flow from **All games** first asks the manager to choose a game.

The manager-only **System** area contains Website API keys, Imports, Helper data, and Webhooks. Normal Clan settings now contains only game, frontend, and Discord configuration. Treat keys, webhook signing secrets, and secret configuration as sensitive: never paste them into articles, roster notes, public screenshots, or support messages.

Each website API key belongs to the currently selected workspace and can read
that workspace's clan-owned data. Give it a recognisable name of at most 80
characters. The full value is displayed once, at creation time; afterward the
dashboard shows only its prefix, creation date, and whether it has been
revoked. Revoking a key takes effect for future requests and cannot be undone:
create and deploy a replacement key before revoking one used by a live site.

Website integrations use the versioned API at `/api/v1`. Clan API requests
use `Authorization: Bearer <API key>`. Game-owned clan data uses **Hell Let
Loose** when no `game` query parameter is supplied, including legacy records;
use `game=hell_let_loose_vietnam`, `game=wardogs`, or `game=all` to select
another scope. List requests are cursor-paginated, default to 25 records, and
are capped at 100 records. Every game-owned returned record has an explicit `gameId`, so a
website can safely cache and combine data from more than one game. The live,
machine-readable contract is available at `/api/v1/openapi.json` and the
interactive reference at `/api/v1/docs`.

Roster and member synchronization can use `updatedSince` on their respective
list endpoints. Member pages contain one record per workspace member even when
that person has assignments in multiple games.

The API currently supports article writes, group create/update/delete, event
create/update, stratmap create/update, topic-preset create/update, squad-preset
create/update, roster update/delete, assignment create/update/delete, the named
event conclude action, and event signup changes. Event
deletion is intentionally unsupported because its roster, match, Discord, and
scheduled-job dependencies have no safe deletion lifecycle. Every write requires an `Idempotency-Key`; repeating the
same request with the same key replays its original result for 24 hours. Group
deletion also clears that group's references from workspace assignments. An
event signup request uses
`POST /api/v1/clan/events/{eventId}/signup` with a JSON `userId` and `group`
(a group string or `null`). It applies the same signup eligibility and
registration-window rules as the dashboard.

Event creation and updates use `POST /api/v1/clan/events` and
`PATCH /api/v1/clan/events/{eventId}` with the same complete event form used by
the dashboard. Referenced signup groups, stratmaps, and topic presets must
belong to the authenticated workspace. Successful creates emit `event.created`;
updates and `POST /api/v1/clan/events/{eventId}/actions/conclude` emit
`event.updated`.

Stratmaps and presets use `POST /api/v1/clan/stratmaps`,
`POST /api/v1/clan/topic-presets`, and `POST /api/v1/clan/squad-presets`, with
the corresponding `PATCH /{id}` paths for complete dashboard-equivalent
updates. These resources are intentionally non-deletable: existing event,
roster, and Discord-forum references do not have a safe cleanup lifecycle. A
stratmap's referenced event must belong to the authenticated workspace and use
the same game. Topic preset attachment limits are the same as the dashboard.

Roster updates use `PATCH /api/v1/clan/rosters/{rosterId}` and must include the
complete roster form for that same event. Only unpublished rosters can be
deleted. Assignment changes use `/api/v1/clan/assignments`; they rebuild the
workspace and user membership state and synchronize open matching-game rosters.
An assignment cannot be moved to another user or game through `PATCH`. Logi emits one
`roster.updated` webhook after a roster write, or after an assignment change
that updates at least one open roster.

`PATCH /api/v1/clan/settings` changes only explicitly supplied safe workspace
and Discord fields. It cannot write runtime credentials, player-stat tokens,
ticket or membership workflows, or game overrides; omitted settings remain
unchanged.

<Callout type="warning">
    Do not rotate, delete, or reveal an API key unless you understand every
    integration using it. A broken key can interrupt an external integration
    immediately.
</Callout>

### Webhooks

System administrators can add an HTTPS webhook endpoint and send a test event.
Logi signs the exact JSON payload using `X-Logi-Signature` as
`sha256=<HMAC_SHA256(timestamp + "." + rawBody)>`; use `X-Logi-Timestamp` to
reject stale requests. The signing secret is revealed only when a subscription
is created or rotated. Current mutation events include article creation, update, and
deletion; event creation and updates; and roster updates caused by API event-signup changes. Failed transient deliveries retry with bounded backoff; permanent
4xx responses do not retry except `408` and `429`. Delivery history records
successful, failed, and retried attempts; deleting or disabling a subscription
prevents queued deliveries from being sent.

## Discord settings: what each field actually enables

Saving a channel or role selection does not prove that the bot can use it. The
bot must still be in this Discord server, be running, and have the channel and
role permissions required for the relevant action.

| Setting                     | Enables                                                            | If blank, invalid, or inaccessible                                                                                                 |
| --------------------------- | ------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------- |
| Timezone                    | Dashboard formatting for this workspace and event-entry conversion | Times fall back to the relevant display default; it does not change existing stored timestamps.                                    |
| Default language            | Bot panel, event, and interaction wording                          | Existing content is not translated; the bot uses its configured fallback where needed.                                             |
| Announcements channel       | Event announcement messages                                        | No announcement is created there.                                                                                                  |
| Event information channel   | Separate match information message                                 | The separate message is not created. It is meaningful only alongside announcements.                                                |
| Errors channel              | Delivery of bot error reports                                      | Errors remain in the bot's logs rather than reaching a staff Discord channel.                                                      |
| Calendar channel            | One managed calendar-panel message                                 | No Discord calendar panel is maintained. Removing the configured channel clears the stored panel state after cleanup is attempted. |
| Forum category              | Match forum-post provisioning                                      | A match cannot get a Logi forum post from the workspace default.                                                                   |
| Meeting voice/stage channel | Discord scheduled event and meeting-channel attendance tools       | No scheduled event is maintained. A text/category channel is not a substitute.                                                     |
| Clan role                   | Clan pings and membership-role transitions                         | No clan ping/managed clan role is available.                                                                                       |
| Dashboard admin role        | Dashboard manager access when Discord member access is synced      | The role does not grant access; Discord Administrator remains an independent access path.                                          |

Event-level Discord channel selections can override workspace defaults at event
creation. Those message locations are then retained for that event; later
editing an event does not move its existing Discord messages between channels.

### Manual calendar items and categories

The frontend settings area also owns manual calendar items and event-category
presentation. Saving this form replaces the workspace's manual calendar-item
set: remove an item there only when you intend to remove it from the calendar.
Categories supply label, colour, and optional emoji; they are visual grouping,
not access control or a Discord role mapping.

## Imports, performance, and helper data

The **Imports** section is manager-only operational maintenance. Each action uses
the game selected in the dashboard game switcher; when no game is selected, it
defaults to **Hell Let Loose**. The exact
member-import and linking safeguards are documented in
[Members and groups](/wiki/configuration/members). Two other controls are easy
to misunderstand:

- **Refresh performance history** rebuilds the workspace and player trend
  snapshots from recorded, non-training events with imported match statistics.
  The charts retain at most the ten most recent qualifying matches. It does not
  import a scoreboard, create a match result, or change a member's stored
  all-time performance summary.
- **Initialize helper data** first clears helper data, then creates the bundled
  default group hierarchy and one HLL Standard Lineup squad preset. It does not
  restore previously customised groups, topic presets, or squad layouts.
- **Reset helper data** deletes this workspace's groups, squad presets, and
  topic presets. It also clears group selections from assignments, topic-preset
  selections from events, and squad-preset selections from rosters. It leaves
  people, assignments, events, and rosters themselves in place. There is no
  recovery action in the dashboard.

Use reset only when deliberately starting these helper structures over, and
check events and rosters afterward because their preset references will have
been removed.
