# Set up the Discord bot

This guide is for the person hosting Logi and the Discord server manager who configures a workspace. The bot is optional for browsing the public site, but it is required for Discord announcements, interactive sign-ups, event forum posts, scheduled events, panels, role automation, and Discord-based attendance features.

<Callout type="warning">
    Never put real tokens, secrets, or API keys in a wiki page, screenshot,
    ticket, Discord message, or Git commit. Use placeholders such as
    `your-secret-here` in configuration examples.
</Callout>

## What you need before starting

| Requirement                                  | Why it is needed                                            |
| -------------------------------------------- | ----------------------------------------------------------- |
| A deployed or running Logi dashboard         | Gives people the site links included in Discord messages.   |
| A reachable Convex deployment                | Stores the shared dashboard and bot data.                   |
| A Discord application with a bot user        | Supplies the bot token and application identity.            |
| Discord server owner or administrator access | Lets you install the bot and select channels and roles.     |
| A long-running bot process                   | The bot polls for changes and handles Discord interactions. |

## 1. Create and configure the Discord application

In the Discord Developer Portal, create or select the application that will represent Logi, then add a bot user. Copy the bot token only into your private environment configuration.

Enable the **Server Members Intent**. Logi listens for member joins, updates, and removals so it can keep dashboard access and role-related automation current. The bot also uses guild and voice-state events.

Use the Logi dashboard's bot-invite flow for the selected server. It requests the permissions Logi needs, including event management and role management. The bot must be above every role it may assign in the Discord role list; Discord will reject attempts to manage an equal or higher role.

## 2. Configure the hosting environment

<Tabs items={["Required for the bot", "Required for Discord sign-in", "Optional network settings"]}>
    <Tabs.Tab>

| Variable                                                 | Value                                                                                         |
| -------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `DISCORD_BOT_TOKEN`                                      | The private token for this Discord bot user.                                                  |
| `NEXT_PUBLIC_CONVEX_URL` **or** `CONVEX_SELF_HOSTED_URL` | The Convex endpoint used by the bot. `CONVEX_URL` is also accepted by the bot runtime.        |
| `INTERNAL_AUTH_SECRET`                                   | A private shared secret. It must exactly match the value configured for the Convex functions. |

    </Tabs.Tab>
    <Tabs.Tab>

The dashboard's Discord OAuth sign-in also needs `DISCORD_CLIENT_ID`, `DISCORD_CLIENT_SECRET`, and a `DISCORD_REDIRECT_URI` (or a `SITE_URL` from which the default callback URL can be built). These identify the same Discord application, but they do not replace the bot token.

    </Tabs.Tab>
    <Tabs.Tab>

Set `SITE_URL` to the public dashboard URL. Discord embeds and links should lead to this address. If the bot and dashboard run in the same private network, `INTERNAL_SITE_URL` can point at the private dashboard origin used to pre-render roster images; public Discord links still use `SITE_URL`.

    </Tabs.Tab>

</Tabs>

For local development, put values in `.env.local`; the bot loads that file from the repository root. Start the bot with `npm run bot:dev`, or start it alongside the dashboard with `npm run dev:all`. Production needs an equivalent supervised, always-on process; the dashboard alone does not run the bot.

## 3. Install the bot and connect the workspace

<Steps>

### Invite the bot to the correct server

Sign in as the server owner or an administrator, select the intended Discord server, and approve the requested permissions. Check that the bot appears in the server member list.

### Sign in to Logi with an eligible account

Open the dashboard, select that workspace, and verify that the workspace recognises the bot as present. The operational manager navigation appears only when the workspace and your access allow it.
If the bot is missing, Logi shows a prominent warning across that workspace with
an **Invite bot** action. Complete the Discord authorization, ensure the bot
role has the requested permissions and sits above every role it must manage,
then use **Refresh** in the warning to confirm the installation.

### Open clan settings

In the workspace, open **Settings → Channels and language**. Logi loads available Discord channels, roles, and emojis through the bot connection.

### Save one small configuration first

Set the timezone and one non-destructive channel, save, then confirm the settings reload correctly. This proves that dashboard, Convex, bot, and Discord can all communicate before you configure the rest.

</Steps>

## 4. Turn on the capabilities you need

Configure only the sections your community will use. Empty optional fields disable the corresponding behavior rather than making the whole bot fail.

The landing page also shows these Discord workflows: membership applications,
event information and sign-ups, attendance acknowledgements, and support tickets.
They are examples of the configured bot capabilities, not separate services.

| Capability                                      | Configure in the workspace                                                                        | What to verify                                                                                                    |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Event announcements and sign-up buttons         | Announcements channel, plus Event info channel when using separate detail posts                   | Create a test event. Confirm an announcement is posted and a test member can respond.                             |
| Event forum posts and briefings                 | Forum category                                                                                    | Create a test event and confirm one forum post is created or updated.                                             |
| Discord scheduled events and meeting attendance | Meeting voice/stage channel                                                                       | Confirm the scheduled event points to the correct meeting channel; test the manager attendance confirmation flow. |
| Calendar panel                                  | Calendar channel                                                                                  | Confirm the bot creates or refreshes the calendar panel.                                                          |
| Bot error reporting                             | **Channel for bot errors** on **Settings → Discord → Messages and panels**                        | Use a channel only managers can read; see [Bot errors channel](#bot-errors-channel).                              |
| Dashboard-admin role sync                       | Dashboard admin role, then use the dashboard's resync control                                     | Add and remove the role on a test account and confirm dashboard access changes after the sync.                    |
| Group sign-up eligibility and membership roles  | Group-linked roles for sign-up/import; clan role and membership category roles for role changes   | Test the two behaviors separately; only membership-category roles are added or removed by the bot.                |
| Ticket panel                                    | Enable ticket settings, submit channel, ticket parent channel, and at least one category          | Confirm the panel appears and a test request creates a ticket in the intended private location.                   |
| Membership application panel                    | Enable membership settings, submit channel, application parent channel, and at least one category | Confirm the panel appears and a test application reaches the intended private location.                           |

<Callout type="info">
    Event-level channel choices can override a workspace default. When a test
    event appears in an unexpected place, check the event's own Discord/channel
    fields before changing the server-wide setting.
</Callout>

## 5. Run a complete safe test

1. Create a clearly named test event with a future time.
2. Confirm its announcement, sign-up controls, event information, and forum post appear only in the chosen test channels.
3. Use a non-manager test account to try sign-up and verify the status is reflected in the dashboard.
4. Create a draft roster, publish only to the test audience, and check any notification option before enabling it for real members.
5. If you use role automation, test it with a disposable role and account before connecting real membership roles.
6. Inspect the bot dashboard/logs for errors, then remove the test event and any test channels or roles when finished.

## Slash commands

Logi registers these eight commands in every server when the bot starts, when
it is added to a server and after the clan language or the command settings
change; **Settings → Discord → Commands** shows the last registration and can
request another. All commands are server-only. Names stay the same; descriptions
and options are shown in the clan language. Every command is visible to
everyone; who may use it is checked freshly from Discord at each use, as set on
the Commands page (see [Discord commands](/configuration/commands)).

| Command                                                | Purpose and access                                                                                                  |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------- |
| `/help`                                                | Private list of the commands you can use here, the channels to use and a link to the guide                          |
| `/stats game:wardogs` or `game:hll`                    | Private player statistics, optional linked member, period and explicit sharing                                      |
| `/server-status game:wardogs` or `game:hell_let_loose` | Private stored game-server status for Logi managers (Administrator or the managers' role, plus extra roles)         |
| `/close_ticket [reason]`                               | Close the current tracked ticket thread; Administrator, configured dashboard-admin role or category support role    |
| `/close_application outcome:<choice> [reason]`         | Close the current tracked application and request the corresponding membership state; same roles as `/close_ticket` |
| `/notice event:<selection>`                            | Open your notice/reason modal for a matching eligible event                                                         |
| `/link`                                                | Privately manage your claimed platform identifiers; this is not verified Steam ownership                            |
| `/player player:<selection>`                           | Privately show a clan player's profile from imported matches, with **Share** to the channel                         |

Brackets mark optional input. Closing reasons are limited to 500 characters.
Application outcomes are `denied`, `pending`, `recruit`, `member` and `mercenary`.
Both close commands check your roles at the moment you use them, the same way:
Discord Administrator, the configured dashboard-admin role or a support role of
the thread's category. Their replies, including "use this inside the thread",
are in the clan's bot language.

Every reply is private and in the clan's bot language. If a button or command
fails unexpectedly, the bot answers only you with **Tohle se nepovedlo** ("Zkus
to za chvíli znovu. Když to nepůjde, napiš správcům klanu."; "That didn't work"
in English clans); details go to the bot log, never to the reply.
Event and player selections support autocomplete. Signup, attendance, ticket,
application and recap-preference buttons are separate workflows, not additional
slash commands. Verified Steam linking is available in your Logi account settings.

## Player statistics

Use `/stats game:wardogs` or `/stats game:hll` for your statistics. Select `member`
to view another linked member of this Discord server. The command reuses the
Steam ID from your Logi application; if it is missing, **Add / change Steam** opens
a private form and reloads the statistics after saving. You can add an ID without
submitting a clan application. Enter a Steam64 ID or numeric Steam profile URL.
This declares the ID for public statistics; it does not prove ownership, grant
clan membership or assign roles. Verified Steam linking stays in account settings.

The default period is 30 days; choose 7, 90 or all recorded history with `period`.
Wardogs additionally supports `player` search by nickname/Steam ID and a `server`
filter. Select either a member or a recorded player. HLL is restricted to linked
members and does not accept arbitrary IDs through the command.

Cards offer an overview and recent games, plus factions for Wardogs or maps and
weapons for HLL. Unknown values stay unknown. HLL's recent-form percentage has
its own last-100-games scope, and `+` counters are lower bounds. Wardogs statistics
cover games retained by this community's Warcon collection.

Replies initially appear only to you. **Share** publishes the current view to the
channel supplied in `channel`, else to the default sharing channel a manager set in
**Settings → Discord → Commands**, or opens a channel picker. Managers can also
switch `/stats` off entirely or for one game, limit who may use it and where;
the bot then answers privately why it cannot be used. You and the bot need
View Channel, Send Messages (in threads: Send Messages in Threads) and Embed
Links there.
Private controls expire after 15 minutes or a restart; run `/stats` again. Shared
cards are snapshots and are not automatically refreshed like server panels.

Live HLL server panels use CRCON independently of profile statistics. They show
the map, online count, Allies/Axis scores, remaining time and optional current-round
kill leaders/private player pages. CRCON and Warcon panels can also open private
[Report Player tickets](/configuration/tickets) in an administrator-selected room.

If no games are found, the Steam link remains saved. If HLL Records blocks
automated access, the bot explains this and links its public profile. A browser
being able to open the page does not prove that the bot can fetch it. HLL Records
only covers tracked community servers; it is not an all-server HLL record.

## Game-server status (server managers)

Use `/server-status` and choose **Hell Let Loose** or **Wardogs**. Only Logi
managers may use it: Discord Administrator or the managers' role, plus the extra
roles set on the Commands page, checked freshly at every use. Others get a
private note and, when the clan has one, the live score channel. The response is
visible only to you.
The command shows up to five stored connections for that game, including state,
player count, map, source and observation age. The footer reports the full count;
open Logi settings for the complete list. Replies use the clan's bot language
(Czech, English or German), whatever language your Discord app uses.

This reads the existing game-data collection. It does not contact or control the
game server. Zero players is a known value; `?` or unknown means data is missing.
Stale data is marked **Stale** and disabled collection **Collection off**, even
when older counts and map names remain visible. A timeout does not mean the server is offline. If no
source is configured, the command explains that instead of inventing a status.

The operator must deploy the compatible bot/backend and configure the collection
first. A person added as a manager only in Logi needs the managers' role or an
extra role on the Commands page to use the command in Discord.

## Bot errors channel

When the bot cannot do something for the clan, it posts a report to the
**Channel for bot errors** chosen on **Settings → Discord → Messages and
panels**. Reports are written in the clan language with a grey bar, never the
clan colour, and contain no error codes, stack traces or IDs. Each report has:

- what failed, for example "The match announcement was not sent", with the match,
  ticket or application it concerns and the channel or role involved;
- **Why**: in plain words, for example the bot lacks the **Send Messages**
  permission in `#oznameni`, the role is above the bot's role, the channel was
  deleted, or Discord did not answer in time;
- **What to do**: the step that fixes it and whether the bot tries again by
  itself, after the fix or not at all, and whether the player was told;
- buttons to the match or the settings page that fixes it (for example
  **Channels and language**, **Roles and access**, **Tickets**).

Pick a channel only managers can read and give the bot **View Channel**,
**Send Messages** and **Embed Links** there. Without a channel the reports stay
in the bot's logs. A member whose direct messages are closed is not reported
here; the match **Overview** shows who a reminder did not reach.

When **Absences and late notices in the match thread** is turned on under
**Messages and panels**, `/notice`, **Running late** and **Can't make it** also
post who is late or absent and the arrival time to the match forum thread,
without the reason. It is off by default.

## Platform status channel (superadmins)

Superadmins can choose one bot-enabled workspace as Logi's platform workspace
under **Platform settings**, with the channel for the status message. The bot
keeps one service-status message in that channel, in the language of that
workspace and with a grey bar: **Everything is running**, the name of the
service that is down, or **We don't know the status right now** when the status
monitor does not answer. Each service shows **Running** or **Unavailable**
with since when, and the message says it is checked every 30 seconds and when
it was last checked. The message is edited in place, not posted again.

Below it the bot keeps a **Status changes** thread, and posts a short card
there only when a monitored service goes down or comes back, with how long the
outage lasted. A thread created earlier under the old name **Status updates**
is renamed; for that the bot needs **Manage Threads** in the channel. It tracks
the same dashboard, Convex, data-store, Discord, and LogiComms dependencies
shown on Logi's public status page. The selected workspace remains a normal Logi
workspace; this adds platform monitoring and does not replace its own clan
configuration.

## Troubleshooting

| Symptom                                       | First checks                                                                                                                               |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| The bot does not start                        | Confirm all three bot-required environment variables exist, the Convex URL is reachable, and the internal secret matches Convex.           |
| The workspace does not show bot-enabled tools | Confirm the bot was invited to that exact Discord server and that the dashboard account can see/select the workspace.                      |
| Channel or role selectors are empty           | Check the bot token, bot membership, and Discord permissions; then reload settings.                                                        |
| The bot cannot assign a role                  | Check **Manage Roles**, then move the bot's highest role above the target role.                                                            |
| No event post, forum post, or calendar panel  | Check the relevant configured channel/category, channel permissions, and the event-level override.                                         |
| Buttons respond with an error                 | Confirm the bot process is running, the internal secret matches, and review the bot dashboard/log scope without sharing sensitive details. |
| Dashboard admin access does not change        | Confirm the configured admin role is correct, then run the manager resync control and allow the bot sync to complete.                      |

## Exactly how Discord roles behave

Logi uses several role mechanisms. They look similar in the settings screen, but their behavior is intentionally different.

| Configuration                                          | When Logi reads or changes it                                                        | Automatic Discord changes                                                                                                                                              |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Dashboard admin role                                   | The bot reads each member’s roles on full sync and on Discord member join/update     | None. The role grants dashboard manager access; removing it removes that access on the next sync/update. Discord's Administrator permission also grants access.        |
| Group-linked role                                      | Checked when a member selects a group for a match; read during Discord-member import | None. It qualifies a group sign-up or imports the group; changing a dashboard group assignment does not grant/revoke it.                                               |
| Clan role plus membership-category recruit/final roles | A manager closes a membership-application thread with a membership outcome           | The bot adds roles required by the new recruit/active outcome and removes roles that belonged only to the old outcome. Pending receives none.                          |
| Event Attendees/Reserves roles                         | During event sync while the event is not concluded                                   | The bot creates or reuses temporary roles, then aligns them to confirmed attendees, rostered players, and reserves. It deletes both roles when the event is concluded. |

<Callout type="warning">
    Every role that the bot must add, remove, create, or delete has to be below
    the bot’s highest Discord role. A group-linked role used only for checking
    sign-up eligibility does not need to be manageable, but the bot must still
    be able to read the member and their roles.
</Callout>

## Membership applications: the hidden workflow

When membership applications are enabled, the panel needs a submit channel, an application parent channel, and at least one category. A category defines the assignment type to create, staff/support roles, any questions, and optional recruit and final Discord roles.

An applicant can have only one open application in that workspace. Opening one creates a private Discord thread, adds the applicant and configured support members where Discord permits it, and creates a **pending** Logi assignment if one does not already exist. Closing the thread records an outcome. A membership outcome updates the assignment and applies the membership-role transition in the table above; a denial closes the application without creating an active membership role set. Thread creation, permissions, and role updates can fail independently, so inspect the bot error channel and the saved application state after a test.
