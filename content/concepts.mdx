# Key concepts

## Workspace

A **workspace** is one Discord server/community in Logi. Everything created inside it—members, events, rosters, articles, settings, and Discord configuration—belongs to that workspace.

## Events, matches, and trainings

<Tabs items={["Event", "Match", "Training"]}>
    <Tabs.Tab>
        An event is a general scheduled activity. It can have a meeting time, a
        game time, sign-up settings, a map, a result, and optional Discord
        coordination.
    </Tabs.Tab>
    <Tabs.Tab>
        A match is an event used for competitive play. Managers can add
        match-specific details, link it to a competition where applicable, and
        record results.
    </Tabs.Tab>
    <Tabs.Tab>
        A training is an event focused on practice. It uses a clear start/end
        schedule and can be completed after it has taken place.
    </Tabs.Tab>
</Tabs>

## Games and game scope

One workspace can run several games in the same Discord server. Logi currently
supports **Hell Let Loose**, **Hell Let Loose: Vietnam**, and **Wardogs**.
Managers enable the games their clan actually plays in **Settings**. This does
not create another workspace, Discord server, or Discord account.

The game selector below the workspace selector controls the dashboard view:

| Selection | What it does |
| --- | --- |
| **All games** | Shows the clan-wide, unfiltered view. Game-owned rows display a game badge so their origin remains clear. |
| A specific game | Shows only records belonging to that game and uses that game's settings and available groups. |

Existing records without a stored game are Hell Let Loose records. This legacy
default preserves existing HLL-only workspaces. A game badge in a breadcrumb or
table row identifies the record's resolved game.

Game ownership applies to matches/events, match-result imports and statistics,
maps and caps, stratmaps, groups, assignments/membership, and membership
applications. General workspace content and a person's Discord/platform links
remain shared.

## Roster

A **roster** assigns people to squads and slots for one event. It can stay a draft while you plan it, then be published when it is ready to share. Players not in a slot can be kept as reserves or marked as not attending.

## Groups and memberships

A **group** is a server-defined organisational label. A member assignment can have one primary group and any number of secondary groups. Groups are separate from membership category, membership status, and Discord roles, even though they can be connected in a few places.

| Thing                     | What it means                                             | What it controls                                                                  |
| ------------------------- | --------------------------------------------------------- | --------------------------------------------------------------------------------- |
| Group                     | Team, unit, language group, or other local classification | Member organisation and group-specific match sign-up choices                      |
| Membership type           | Member, reserve member, or mercenary                      | Whether a person belongs to this workspace or is attached as a mercenary          |
| Membership status         | Pending, recruit, or active                               | Match sign-up eligibility and, when configured, membership-category Discord roles |
| Linked group Discord role | An optional Discord role stored on a group                | Eligibility for that group’s event sign-up choice and Discord-member imports      |

### What a linked group role does—and does not—do

If a group has a linked Discord role, a Discord member who holds that role can choose that group on an eligible match sign-up. A manager-assigned primary or secondary group also qualifies that person for the matching group sign-up, even if Discord does not currently show the role.

During **Import Discord members**, Logi can use linked group roles to populate the imported member's secondary groups. This is a one-way import at that time.

<Callout type="warning">
    Linking a Discord role to a group does **not** make Logi continuously add or
    remove that group role in Discord. Changing a member’s group assignment in
    the dashboard does not change their Discord group roles, and changing the
    Discord role does not continuously rewrite their dashboard groups. Keep
    those two records aligned deliberately, or run the relevant import workflow.
</Callout>

### Roles the bot does manage

The bot does add and remove two different kinds of roles when they are configured correctly:

- Membership roles: completing a membership application can apply the workspace clan role plus the category’s recruit or final roles. Changing the application outcome removes the roles associated with the previous outcome and adds the roles for the new one. Pending has no automatic membership roles.
- Event roles: for an active event, the bot maintains temporary **Attendees** and **Reserves** roles from the event’s attendance and roster. It deletes those temporary roles when the event is concluded.

In both cases, Discord still requires the bot to have **Manage Roles** and to sit above every target role in the server role list.

## Status and visibility

<Callout type="info">
    Status tells you where something is in its lifecycle; visibility controls
    who can see it. An item can be visible before it is complete, so always
    check both labels.
</Callout>

Terms such as **draft**, **published**, **confirmed**, **declined**, **pending**, and **completed** appear in context. They are not interchangeable: for example, publishing a roster shares its current assignments, while confirming attendance records a person’s attendance state.
