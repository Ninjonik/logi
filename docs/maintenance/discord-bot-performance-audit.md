# Discord bot performance and maintainability audit

Status: bot source/test review complete, 2026-11-11. All **135 source/support-code files and 98 test files** under `discord-bot` were fully read. The bot README and TypeScript configuration were also reviewed. Counts, hashes and dispositions are in [the ledger](discord-bot-review-ledger.json). No application code was changed. Performance-relevant backend/shared paths were traced separately; this is not a claim to have manually audited the entire application or every transitive dependency.

The bot has useful safeguards, but I would not call its performance established at scale. The largest risks are work amplification across guilds/history, missing aggregate concurrency limits, incomplete crash recovery, repeated Discord operations and retained dynamic state. The [implementation plan](discord-bot-implementation-plan.md) covers every finding below, with completion criteria. No remediation package is implemented yet.

Backend checkpoint: full reads of `convex/discordSync.ts`, `discordCommands.ts`, and `scheduledJobs.ts` confirm global guild/config subscriptions and the global event index. The event selector uses `status_gameEnd` to exclude the concluded archive, which is good; the remaining active-event set is still global and unbounded, and the index returns whole rosters. Signup context collects every assignment in the clan for one user's click. Add a narrow caller assignment projection and compact roster/event revisions; retain game scope and shared-match projection. Scheduler recovery collects all jobs; startup backfill collects the entire events table on every restart. Replace repeated migration/backfill scans with durable bounded cursors and indexed periodic expired-claim recovery. `claimDue` reads up to 500 rows and continues loading/maintaining later candidates after filling the requested claim count; separate bounded cleanup from claiming and measure transaction reads/writes. Claim/release/complete currently identify jobs by ID without an attempt fence; stale completion must not delete a newer claim after lease expiry. Delivery handoff semantics remain a separate contract decision.

All 98 test files were reviewed. The bot suite passed **648 tests, zero failures, zero skips**, on Node 24.22.1 in 18.44 seconds. Notable gaps: sync-service tests cover delay calculation only; sync/events tests cover ping selection rather than the whole workflow; publication adapter tests do not cover deleted-channel recovery; image tests do not establish streamed byte limits or cache lifecycle; registration tests do not cover concurrent cold loads or request coalescing. Existing tests require fresh authorization, six-hour member reconciliation, failed-fetch backoff, complete privacy pagination, immutable attachment reuse and stats history budgets. Preserve these while adding controlled-time/call-count/concurrency regressions.

The test invocation used `node --import <temporary-offline-loader-file-URL> --import tsx --test "discord-bot/src/**/*.test.ts"`. The temporary loader disabled dotenv file loading and supplied synthetic credentials/loopback URLs; application environment files were not inspected. The first invocation used a Windows path instead of a file URL and failed before tests loaded (`ERR_UNSUPPORTED_ESM_URL_SCHEME`); the corrected run passed. SDK gateway tests use an offline loopback fixture. No live Discord, configured Convex deployment, production load test or heap profile was run. Two initial adapter-probe attempts were stopped after an incomplete mock attempted the synthetic localhost connection; the corrected CommonJS probe mocked all backend methods and completed offline.

## Source findings

- GuildCache.applySnapshot repeatedly finds/filters whole global arrays per guild and rebuilds every signature. Group records once by guild and use compact scoped revisions; preserve removal detection. Confirm backend subscription read/byte amplification before choosing watcher topology.
- DiscordSyncService globally serializes guild/event processing. Full guild sync loads all eligible event contexts concurrently without a concurrency cap. Calendar refresh repeats all those context reads. Several changed events can each trigger the same guild-wide calendar assembly. Coalesce calendar work per guild and reuse bounded per-cycle contexts without weakening current-state checks.
- The sync queues are cleared into local snapshots before work. Failures are logged without requeue in the inspected loop. Trace publication retries versus lost non-publication intent; do not indiscriminately retry ambiguous Discord creates.
- utils.withTimeout races a promise but does not cancel it. runGuildSyncStep can start the next step while the old timed-out operation keeps running. Timeout is not a concurrency bound. Trace every caller and use cancellation or retain ownership until actual completion.
- Startup discards many worker stop handles and has no coordinated shutdown. A failure starting meeting attendance or sync can prevent later services and fallback scheduling from starting. Review dependency-specific startup retries/readiness instead of blanket swallowing failures.
- Cache invalidation retries are finite and outcomes do not throw, which preserves committed business success. They still occupy the caller for up to three request timeouts and waits; check every awaited caller and coalesce repeated tenant/resource invalidations. Durable recovery requirements depend on cached-data freshness guarantees.
- Fallback recurrence awaits cache invalidation for each generated event before normal due-job processing. A slow website can therefore delay schedule processing substantially. Separate authoritative scheduler progress from cache HTTP delivery, with bounded/coalesced effects.
- Fallback consumes scheduled reminder jobs before parent-process delivery; durable delivery/recovery semantics need the previously recorded A26 review. README explicitly documents partially delivered reminder reservations, so any semantic change must preserve or deliberately revise that contract.
- Frequent informational logging occurs on enqueue, scheduling, index updates and flushes; bot log delegates to synchronous shared SQLite logging. Measure event-loop delay/write contention and ensure logger failures cannot crash otherwise successful work.

The detailed notes below retain the individual call sites so implementation agents can address the whole family. Questions phrased as “trace” identify implementation design checks, not unread bot files. The dependency conclusions and policy constraints at the end supersede provisional interpretations in those notes.

## Additional source evidence

### Detailed evidence by subsystem

- `forum.ts:buildDiscordAttachments` fetches attachments without a deadline or cancellation, buffers the entire body before enforcing individual/aggregate limits, and redownloads attachments when unchanged topic starters are edited on every event sync. Add streamed byte/deadline limits, versioned attachment reuse, change fingerprints, bounded external-download work, and explicit response cleanup. Preserve sequential send ordering and total upload limits.
- `forum.ts:findForumPost` fetches active posts before trying a stored ID and searches only the first hundred archived posts on fallback; swallowed fetch failures can lead to new duplicate posts. Prefer direct stored-ID resolution, distinguish confirmed missing from unreadable, and make recovery pagination bounded and resumable rather than treating an incomplete search as proof of absence. Private debrief recovery does paginate with progress checks, but can traverse the entire archive in one event pass; preserve its no-duplicate guarantee while adding a resumable work budget. Forum metadata, starter cards and topic names are edited unconditionally; use desired-state/content comparison. Topic follow-up messages are sent on creation but existing follow-ups are not reconciled when the preset changes; extraction must preserve all message blocks and durable IDs, not only optimize the starter.
- `player-reports.ts:verifyAccess` enumerates up to ten thousand guild members for privacy proof. Opening calls it twice around provider loading; submitting/delivering can add several more complete enumerations. This is a real expensive security requirement in the current model, not safe to remove blindly. First perform cheap source/reporter checks, coalesce concurrent complete inventories only within a defined fresh authorization generation, preserve post-provider validation, and design a versioned privacy-proof/invalidation model if measurements justify it. Keep complete enumeration, unexpected-reader rejection and fail-closed behavior; page budgets must not turn incomplete proof into permission. Recovery globally scans guilds serially, so apply the same fair due-work scheduling plan.
- `interactions/event-buttons.ts` holds its per-user/event lock while waiting up to five minutes for a late-signup modal and while cache HTTP/Discord effects run. Move form waiting outside the mutation serialization boundary; re-read current event/membership at submission and keep atomic backend invariants. Bound/reject duplicate queued clicks rather than retaining unlimited interaction closures. Ranked signup recalculates the same picker/eligibility several times per click; compute once per current context, preserve its revision claim and 1,000-draft cap.
- `interactions/stats.ts` autocomplete calls the history aggregate and scans every retained session/player to produce 25 options. Introduce a narrow paginated/search-index projection for distinct player/server choices, authorization first, short deadlines and shared safe in-flight reads. Existing aggregate caching reduces repeated backend reads but not repeated CPU scans or uncancelled first builds. Stats state maps already have caps (500 cards, 1,000 command cooldown entries); retain them.
- `interactions/tickets.ts` performs a full guild member fetch for each new ticket, even with no support roles. Skip provably unnecessary enumeration, share bounded support-membership reads where safe, and aggregate repeated invitation failures rather than performing an error-report lookup/send for every failed member. Thread creation precedes record persistence and has no visible interaction-id claim; inspect backend deduplication and recovery before proposing retries. `interactions/link.ts` platform emoji initialization lacks in-flight sharing and permanently caches an empty successful list; reuse the application emoji service with deliberate refresh/negative caching. Full source reads found no additional material performance concern in the static type definitions, board fixtures/dump renderer, or the offline gateway fixture.

- `interactions/membership-application-cache.ts`: each remembered applicant sweeps the entire applicant map, producing quadratic insertion work during bursts; expired entries remain during inactivity and there is no maximum live size. Use bounded expiry/LRU maintenance, remove expired entries on read, and separate applicant reads from authoritative definition revisions so a slow applicant-state response cannot overwrite a newer subscribed definition.
- `interactions/membership-web-submissions.ts`: starts every queued web submission concurrently and discards the subscription cleanup handle. Add bounded admission before claims and stoppable/drainable lifecycle. `membership-application-create.ts` fetches all guild members even when individual support invitations are disabled; skip that fetch in that branch. When invitations are enabled, retain explicit complete support membership policy and handle failed enumeration intentionally rather than trusting an incomplete SDK cache. Awaited website invalidation currently precedes thread provisioning and can unnecessarily consume submission lease time.
- `rosters/roster-change-service.ts` has the same overlapping `processAll` issue as manual reminders: per-ID deduplication is not an aggregate cap. Delivery scans changes per recipient and resolves member names even when no digest/DM needs them; index once and gate reads. Keep first-publication mentions and digest baseline semantics while moving long DM fan-out into bounded delivery work.
- `public-panels/calendar.ts` expands recurring calendar items over 367 days before fitting the displayed entries, and repeatedly searches sync states/categories per event. Trace the shared expansion and fitting limits, then request only the horizon/number needed with a correctness-preserving nearest-occurrence algorithm. Preindex states/categories once. Do not truncate before category filtering or lose multi-day entries.
- `public-panels/interactions.ts` reads every guild panel twice to resolve one player-list panel. Add a narrow authorized panel-by-ID projection; preserve the intentional post-load revision/visibility recheck. Language and style are requested serially even though they share one cache record; read one kit or share an in-flight config request.
- `interactions/stats-runtime.ts` already has four active history builds, same-key promise sharing, a 25-second build deadline, at most 200 pages, row/player weight limits, 60-second results and bounded cache weights. Preserve those protections. Individual raced queries can continue after timeout; measure underlying outstanding work separately. Cache permission freshness and requester sharing need backend trace before changing keys. `match-recap-preference.ts` scans guilds serially for membership merely to find a language on legacy/invalid buttons; validate before discovery and prefer known event/guild context or deterministic fallback over cross-guild REST probing.
- Attendance/notice/self-group flows await cache invalidation before enqueueing visible Discord synchronization and before confirmation. Keep authoritative write success separate from optional HTTP delivery latency; enqueue durable/coalesced refresh effects promptly and surface completion accurately. Ticket close commits before its Discord effects with no visible adapter retry on already-closed requests; trace backend receipt/recovery before planning resumable close effects. Never replay an already-sent DM blindly.

- `events/announcement-sync.ts` downloads/builds thumbnail and generated match image before deciding whether the announcement should be skipped or migration-deferred. Derive the cheap lifecycle/migration decision first, then obtain media only for actual publication; share the context and generated image across announcement/details/result work where versions agree. `sync/events.ts` downloads the same published roster image in split-channel details and again for the announcement path, even when that announcement is invisible. Request each required immutable media version once per event attempt and skip unused branches. `publication-files.ts` does not recognize `logi-match-<hash>.png` filenames as reusable, so repeated edits can re-upload immutable match images despite content-addressed names.
- `scheduled-events.ts` edits scheduled metadata whenever synchronization reaches it, without comparing desired metadata to fetched state. Skip equal patches and update lifecycle independently. Fetch failures are treated as absence, potentially creating replacements on transient failure. `events/squad-voice.ts` similarly treats every channel-fetch failure as absence and can create duplicate voice resources; cleanup deletes swallow failures then return an empty ID list. Distinguish explicit missing resources from transient/permission failures, preserve unfinished cleanup IDs, and persist provisioning progress before subsequent operations can fail. `events/signup-thread.ts` adds every attendee on every sync with unbounded concurrency and sets invitable false unconditionally; use bounded membership delta/reconciliation and avoid equal property writes without relaxing privacy.
- `sync/events.ts` writes a full synced version after some scheduled-event failures were swallowed; intermediate forum state can also advance version markers before remaining work completes. Trace each desired-effect completion independently so failed effects remain due without replaying successful expensive effects. This is both a recovery and amplification issue, not a reason to retry every create indiscriminately.
- Automatic/manual reminder delivery is predominantly serial per recipient, so large audiences occupy the invoking sync/request path for a long time. Introduce bounded recipient batches and a shared DM budget, independent of panel/event synchronization. Preserve the existing scheduled reservation policy unless deliberately revised. Attendance reminder loops repeatedly scan reminder logs per user/offset; index existing log keys once. Signup recipient filtering searches the event roster for every assignment; resolve it once. These CPU improvements are secondary to network scheduling.
- `sync/match-recaps.ts` has no visible per-event in-flight guard or pre-send durable claim in the bot adapter; result panels and event synchronization can both invoke it. A read/prepare/send/mark flow can duplicate a DM when two invocations race, or when send succeeds and mark fails. Trace backend preparation before finalizing severity. Use explicit delivery state/lease and uncertain-send policy, bounded retry/backoff for closed DMs, and incremental pending work rather than reconsidering every historical result every minute. Preserve fresh opt-out/account binding checks immediately before sending.
- `error-reporting.ts` performs backend context and several Discord lookups per report with no general storm aggregation/backoff. Managed-role reports already group failures for sixty seconds; extend equivalent bounded deduplication by source/resource/cause where appropriate. Preserve distinct actionable errors and recovery notices. Logging/reporting failure must never suppress the original response or release ownership incorrectly.
- `interactions/acknowledgement.ts` expires prepared modal state after five minutes and validates user identity, but each slow modal retains a collector, interaction, closure and timer until click/expiry. Add measured global/per-user admission limits, deterministic cleanup and shutdown disposal. Autocomplete backstop answers empty after one second but does not cancel backend/provider work; debounce/coalesce safe read-only searches and enforce a work budget separately from acknowledgement timing.
- `public-panels/player-details.ts` intentionally rechecks current panel revision and visibility after live data loads. Preserve this security boundary; repeated reads are not automatically waste. `tickets-report-members.ts` already paginates REST membership, caps ten pages and fails closed on incomplete inventory. Preserve completeness for privacy decisions; do not replace it with a partial cached member list.

- `public-panels/worker.ts`, `seed/worker.ts`, `league/worker.ts`: timer overlap guards exist, but each pass walks every guild serially. Slow rendering, provider reads, result-history replay or Discord writes cause head-of-line blocking and postpone panel heartbeat until the entire panel pass ends. Use fair bounded guild scheduling, bounded work per visit, and an independent heartbeat. Preserve per-panel/per-guild serialization and durable publication ownership. Poll compact due-work/revision projections rather than full guild panels/state on every 15/20/60-second tick; backend queries must be traced before final design.
- `seed/worker.ts:refreshSeedGuild`: after forty 250-ms waits it starts another pass even if the first still runs. Either run then deletes the shared `running` marker. Replace the wait loop with an actual shared promise/serialized refresh and coalesce force requests; a timeout must not release ownership of unfinished work.
- Seed controls refresh every sixty seconds even unchanged; each control checks channel privacy through `channelAccess`, fetching channel and full role definitions. Live/combined/League panels perform similar checks. Share fresh permission facts within a bounded pass where identical authority is sufficient; keep privacy checks before any password/control disclosure. Do not introduce an unbounded or stale cross-pass permission cache. Seed role counts fetch the full guild membership; inspect delivery policy to ensure this is restricted to initial notification and use an explicit complete observation/count contract.
- `public-panels/panel-runner.ts`: combined panels start provider reads and map transforms for every server concurrently. Bound fan-out by configured/server limits and shared provider/image budgets. Live panels always read running-match context, even when content may not show it; gate optional reads by the domain view's actual requirements after tracing its policies. Results pages are paginated at the port, but a pass traverses all history through `synchronizeResults`; unchanged binding hashes avoid Discord writes, not repeated database reads, rendering, hashing or recap attempts. Design incremental dirty-result work plus occasional bounded repair sweeps, preserving removal/privacy changes and resumable cursors. `league/panels.ts` reads the same narrow bindings multiple times per pass; fetch once and update local binding state as writes complete.
- Worker maps (`due`, paused/map memory, image source cache, seed memory) are not pruned when panels/guilds disappear. `createPanelImageSource.forget` exists but the worker never calls it. Add explicit lifecycle cleanup and byte-bounded image eviction. Catalog artwork/map caches have finite catalog keys; do not conflate those with unbounded dynamic panel keys. Remote images use a 200-entry whole-map clear rather than byte accounting/LRU; preserve promise sharing without eviction storms or deleting a newer replacement after an old failed promise settles.
- `public-panels/score-image.ts` and `assets.ts`: response bodies use `arrayBuffer` before enforcing the actual byte cap. A missing/false Content-Length can allocate far beyond 4/8 MiB; stream with a running cap and abort/cancel on excess. Consume/cancel rejected responses too. Native image decoding has pixel limits for resized map assets, which should be retained. Generated score/banner requests have no in-flight sharing in their own source; worker serialization currently reduces but does not eliminate duplicate paths.
- `sync/publication.ts`: previous-channel recovery checks raw Discord error code 10003, but its channel helper has already translated that into `PublicationChannelError('channel_missing')`. The intended deleted-old-channel recovery therefore throws instead of returning absence; add a focused adapter regression before fixing and ensure permission failures still retain bindings. Publication operations repeatedly force-fetch the same channel/bot member, and existence/edit can fetch the same owned message twice. Reuse proven facts within an owned attempt where safe; preserve fresh ownership checks and the durable uncertain-create protocol. Hashing/reuse and immutable attachment retention already prevent some redundant Discord work.
- `league/worker.ts`: retirement checks still query every guild every minute indefinitely after migration; replace with bounded durable migration work or an explicit completed marker plus repair path. Human-message intake queries input settings for every non-bot guild message before rejecting unrelated channels; use a subscribed compact settings projection for early rejection, revalidate writes server-side, preserve edited/deleted-message cleanup. The 100-item intake cap silently drops overflow including deletes, and permits up to 100 independent active message keys. Bound active work separately from backlog, expose drops/age, and define recovery for stale deleted links. Replied-before-send semantics deliberately avoid duplicates but lose delivery after failures; document rather than silently replacing this with automatic retries.

- `commands/guild-configs.ts`: concurrent cold `get` calls each start a global list read; the 1.5-second race does not cancel it. Add shared in-flight initialization and explicit retry/backoff. `runtime/clan-language.ts` has the same per-guild cold/stale read fan-out and retains guild entries indefinitely; unify with live command configuration where appropriate, preserve stale fallback, and evict departed guilds.
- `commands/registration.ts`: guild registration calls chain new runs rather than sharing one run. Ready registration sets commands for every guild even when the stored signature matches. Coalesce requests into one current run plus one newest pending revision, bound startup concurrency, and retain an explicit forced drift-repair policy. Handle failures before the current inner try block and dispose timers/maps on shutdown.
- `commands/access.ts` and `commands/share.ts`: fresh role/member/channel reads are intentional authorization checks. Preserve their freshness; optimize only demonstrably redundant reads within the same authorization boundary, never by substituting stale permission caches.
- `meeting-attendance.ts`: launches every pending request with detached promises. Five concurrent candidate reads per request in `meeting-attendance-members.ts` do not bound aggregate load across requests. Add a bounded dispatcher and tenant fairness before claiming work; preserve the shared REST abort deadline, complete-result validation, and backend claim semantics. Catch detached task failures even if logging fails.
- `manual-reminders.ts`: each `processAll` invocation is sequential, but overlapping subscription callbacks may start other requests while the first is in flight. The per-ID set deduplicates identities rather than bounding total active requests. Use a shared bounded dispatcher and await its shutdown.
- `event-roles.ts`: starts all member role updates before `Promise.all`, with up to two REST writes per member. `sync/member-access.ts` similarly starts every admin override concurrently. Apply a shared Discord write budget with bounded per-guild work and latest-state reconciliation; do not merely rely on the SDK's downstream rate-limit queue. Preserve per-member failure isolation. Investigate empty member-ID fetch behavior and transient fetch failures before allowing role creation or cleanup decisions.
- `sync/membership-ingress.ts`: full membership reconciliation already has a six-hour normal cadence, fifteen-minute failed-fetch backoff, 100-member write batches, and bounded finish pages. Preserve those protections and the complete-fetch/epoch fence. Its per-guild ingress serializes all member observations but has no admission or backlog measurement; gateway bursts can retain many closures. Add queue-depth/age metrics before choosing safe batching that preserves revision/order semantics.
- `sync/managed-member-roles.ts`: recovery worker already limits a pass to four guilds, rotates fairly, prevents overlapping ticks and per-guild operations, and uses durable claims/fences. Preserve this design. Capacity is at most four claim attempts per ten-second pass, lower when work is slow; measure due-operation age and use bounded draining/adaptive wakeups if required rather than scanning every guild more often.
- `platform-status.ts`: interval has no in-flight guard, so a slow pass can overlap the next pass and race message creation/change reporting. Use single-flight execution and stop/drain support. Message edits include a changing check timestamp, so unchanged service states still intentionally update Discord; choose and document a freshness cadence before suppressing those edits.
- `runtime/application-emoji.ts`: provisioning already shares an in-flight promise and backs off five minutes after failures, with hourly normal checks. Retain this. Its interval has no returned stop handle. No material performance issue found in the command builders, fake interaction helper, map formatting, interaction dispatch or message-kit adapter during full reads; their domain/helper dependencies still need closure.
- `sync/panels.ts`: calendar panel lookup errors become `undefined`, which falls back to legacy settings and may write during a backend read failure. Fail closed/retry on unreadable policy, while retaining the legitimate absent-panel fallback. Separate content changes from broad `updatedAt` changes before using calendar fingerprints to avoid refresh amplification (`sync/work.ts`).

## Dependency conclusions and constraints

- `convex/eventReminders.ts` and `rosterChanges.ts` discover only pending rows, although claim handlers accept processing claims older than five minutes. Crons do not return these to pending. Housekeeping deletes old reminder history and finished roster requests; it does not repair abandoned processing work. Add indexed expiry discovery and attempt fences. Meeting attendance instead has a strict 45-second authority deadline; expired work must fail visibly, never be replayed as a late confirmation. `discordRosters.ts` already checks that deadline at the authoritative write.
- `convex/membershipApplications.ts` uses two-minute submission and one-minute decision leases, with unfenced release operations. Queued web discovery reads the first 25 claimed rows and filters expiry afterwards; newer eligible expired rows can be hidden. A query using `Date.now()` does not itself create a wakeup at lease expiry. Add an indexed due time and explicit periodic/scheduled wakeups. `discordMembership.ts` creates ticket records without an interaction operation receipt; application draft deletion after creation does not fence an already-running old attempt. Membership decision workflow spans multiple mutations; preserve the intended game/category change while making the command atomic and external effects recoverable. Current tests deliberately report some late Discord failures as manual repair, so changing that policy requires corresponding copy/docs/tests.
- `convex/matchRecaps.ts:prepareDelivery` is a query, not a claim. Concurrent prepare/send/mark paths can duplicate sends. `listPendingForEvent` reads every status for the event and evaluates delivery eligibility for each; the Wardogs panel/publication checks occur before the pending-recipient rejection. Move cheap terminal checks first and select pending/due work by index. Keep opt-out, source identity and successful-publication requirements fresh at send time. No exactly-once guarantee is possible from a database lease alone after an ambiguous Discord send.
- `convex/discordSeedBot.ts` reads all guild seed-message rows and seed publication bindings and searches outbox arrays repeatedly. Housekeeping does remove delivered terminal runs/outbox rows after the retention window, so those rows are **not all retained forever**. Publication-prefix reads can still include historical bindings, and retained-month volume is unnecessary for an active-call refresh. Read active/unsettled keys directly; retain bounded repair and operational history. Seed delivery's full role-member count is already restricted to the initial call without a recorded post: preserve that guard.
- `convex/discordPublicPanels.ts:forGuild` repeats source/join resolution for connections shared by several panels and searches plans/status arrays per panel. Memoize immutable per-query connection projections; separate due-work summaries from full rendering payloads. `resultsPage` paginates 100 event rows, but its consumer traverses all pages and builds expensive result cards before the final selection. Add progress/cursor guards and incremental public-result projections, including explicit withdrawals and redactions.
- Provider actions are **not uncached raw requests on every panel**. `hllLiveReads.ts` uses source generation, a 35-second lease, provider refresh budget, separate payload/freshness rows and pruning. `warconReads.ts` additionally limits each connection to 30 reserved reads/minute and caps cached query variants at 64. `provider-http.ts` already enforces streaming response limits, request aborts, a 30-second request-lifetime budget and address policy. Preserve these; bot-side fan-out still incurs action/reservation/auth overhead and must be bounded. Credential resolution and DNS work need their own measured deadline treatment before claiming end-to-end cancellation.
- Installed Discord.js uses a 200-message-per-channel default, while unspecified managers use ordinary collections. This supports measuring member/user cache memory, not an unsupported claim that all SDK caches are unlimited. Fetching `{user: []}` still enters its multi-member gateway request path; guard empty work before calling it. Do not replace a complete privacy inventory with SDK cache contents.
- Calendar display fits ten rows, but the adapter first expands a year and the shared expander iterates from the series start with a 512-occurrence ceiling. Seek to the overlap window, maintain occurrence identity, and handle invalid dates/month skipping without duplicate/skipped occurrences. This affects shared calendar behavior, so update its other consumers/tests when implemented, without expanding this audit into the rest of the app.
- `src/lib/system-logs.ts` uses synchronous SQLite writes with per-write statement preparation; normalization can recurse into cyclic error causes before the write's catch. No retention/WAL/busy policy is established in that file. Measure actual host policy instead of assuming no external rotation exists. Make hot-path logging bounded and failure-safe; aggregate repeated Discord error reports.

## Coverage and what passed review
